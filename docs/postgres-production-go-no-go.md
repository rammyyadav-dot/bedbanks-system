## Production operating-model review

The reviewed implementation uses `PrismaService.withTenant()` to establish `app.current_tenant_id` with transaction-local `set_config(..., true)`. The intended normal HTTP database role is non-owner, non-superuser and must not have `BYPASSRLS`.

The policy design requires four separately governed role classes; production names and credentials are intentionally not recorded here:

| Role class | Approved responsibility | RLS/bypass expectation |
|---|---|---|
| Migration owner | Forward-only schema deployment during an approved window | Not for HTTP traffic |
| HTTP application role | Normal authenticated API requests | Non-owner, non-superuser, no `BYPASSRLS` |
| Restricted background/system role | Explicitly approved system events, retention or legal-hold work | Controlled and audited; never ordinary HTTP |
| Read-only operational/audit role | Approved diagnostics and audit access | Least privilege, no application writes |

The disposable PostgreSQL tests demonstrate that an ordinary non-owner role cannot cross tenant boundaries, cannot act without tenant context, cannot update or delete ledger/audit records, and cannot create `SYSTEM` audit events. The runtime role configuration remains a database-owner release gate.

## Currency governance

The reviewed application validation rejects lowercase, padded, malformed and unsupported values. No invalid currency is silently uppercased or defaulted at the validation boundary.

## Exact release procedure after checklist completion

1. Database Owner confirms every gate above with secure evidence and obtains sign-off.
2. Release owner verifies the target commit and the ordered committed migration chain; no historical migration may be altered.
3. During the approved maintenance window, the authorised migration owner runs the approved forward-only deployment procedure.
4. Verify migration status and drift using the approved production-safe runbook; capture results in the secure release record.
5. Validate non-owner HTTP role behaviour, tenant isolation and connection-pool reset behaviour using approved non-production-safe probes or controlled production verification approved by the Database Owner.
6. If a fault occurs, stop the release, preserve evidence, and use a reviewed forward-only corrective migration or application rollback. Do not use `db push`, `migrate reset`, destructive repair, or guessed reconciliation.
7. Only after all evidence is recorded may Product/CEO approve production booking enablement.
