# fBeds Tenant Control Center — audit report

**Date:** 11 October 2026 · **Verdict: HOLD production release; retain draft PR.**

Audited application commit: `9f513df01d60b1719740cc192fcc9874c2b60d63`.
PR: [#300](https://github.com/rammyyadav-dot/bedbanks-system/pull/300).
Scope: tenant discovery/onboarding, profiles, memberships, compliance/lifecycle,
Settings context, dedicated database privileges/RLS, UI and execution evidence.

This is an implementation and evidence audit by the implementing assistant, not
an independent penetration test. Existing test logs were inspected; no new
application tests, load tests, production database checks or exploit attempts
were executed during this audit. Code findings below are static findings unless
explicitly described as previously tested. No application fixes are included in
this report.

## Executive assessment

The implementation has meaningful safeguards and passing targeted checks. It
does not fulfill the entire enterprise module specification or establish a
green full-repository regression result on the final integrated tree. One high
release-assurance finding and four medium code/operational findings remain.
No critical exploit was established in this limited review; this does not
certify absence of vulnerabilities.

## Findings

### A-01 · High · Final full regression assurance is incomplete

**Status:** Confirmed evidence gap; release blocker, not a demonstrated exploit.

The full E2E pipeline failed before integration of newer `main`. The final tree
has passing targeted tests, but the entire pipeline was not rerun against it.
Earlier failures include hardcoded `/opt/cursor/artifacts` paths, supply fixture
conflicts and probe-role table resolution. Some may differ after main's fixture
changes; their status on the final tree is unverified.

**Action:** Make artifact output portable, investigate probe-role schema access,
align fixture sequences with canonical currency/stock rules, and run the complete
pipeline on the exact release candidate. Preserve strict-role security tests;
do not weaken validation to obtain a pass. Acceptance: complete CI evidence on
the release SHA, with skipped tests explicitly justified.

### A-02 · Medium · Legacy membership changes lack effective version checks

**Status:** Confirmed static defect; not dynamically reproduced in this audit.

`version()` treats a missing control profile as version zero. Membership changes
accept that version, then increment the profile with `updateMany`; if no profile
exists, zero rows change. The UI also sends version zero for legacy tenants.
Consequently, two distinct stale commands can both pass the version check and
apply sequentially. The tenant lock preserves final-owner protection and
serialization, but does not detect the stale second command.

**Evidence:** TenantControlService lines 61–64 and 170–189;
TenantDetail lines 23 and 26. The existing concurrent-edit test covers a tenant
with a profile, rather than this missing-profile case.

**Action:** Use a governance revision that exists for every tenant, or require
and initialize a profile before governed membership mutations. Acceptance: two
distinct concurrent membership mutations carrying the same legacy revision
produce one success and one 409, with only the winner's mutation/audit applied.

### A-03 · Medium · Directory transaction nesting risks pool contention

**Status:** Confirmed transaction structure; availability impact is an untested
load risk rather than a measured outage.

Directory work holds an outer platform transaction while `Promise.all` opens a
separate scoped transaction for each tenant's member/activity metrics. Page size
can reach 100, and the provisioned authoring login has connection limit ten.
Concurrent directory calls can occupy connections with outer transactions while
their inner transactions queue, resulting in timeouts or pool starvation. The
current single-browser and small-page tests do not establish capacity.

**Evidence:** TenantControlService lines 71–100; TenantDirectoryDto line 14;
PrismaService lines 114–135; tenant-control-role line 9.

**Action:** Complete the directory transaction before opening bounded scoped
metric transactions, or design an explicitly reviewed batched read. Maintain
tenant isolation. Acceptance: concurrent page-size-100 requests against the
configured pool meet a documented latency/error budget without starvation.

### A-04 · Medium · Authoring-role checks are partial and cached

**Status:** Confirmed implementation limitation; no overgrant was observed.

The connection validates restricted identity and selected prohibited grants,
then caches success for its lifetime. It does not compare all effective table,
column, schema and role privileges against an authoring allowlist. Provisioning
revokes table grants from the group but does not constitute an exhaustive audit
of direct login grants, inherited grants or historical column grants. The 18-test
suite checks selected protected reads and ordinary API grant conformance, not a
complete authoring-role drift contract.

An accidental later grant outside the checked finance/booking/password set can
therefore escape these checks. This is an operational hardening gap, not proof
that current fresh provisioning has excessive privileges.

**Evidence:** TenantControlDatabase lines 17–22; tenant-control-role lines 8–20;
tenant-control.e2e-spec lines 51–57.

**Action:** Define and verify the entire effective authoring privilege contract,
including forbidden audit UPDATE/DELETE, tenant DELETE and unrelated writes.
Validate provisioning after rotation and deployment, and monitor drift without
silently broadening grants. Acceptance: deliberate extra grants and inherited
permissions are detected and cause certification to fail.

### A-05 · Medium · Lifecycle retries are not consistently idempotent

**Status:** Confirmed static retry paths; not dynamically reproduced here.

Lifecycle request handling checks current version/status before looking for its
existing request. Replaying a successful request after state/version advancement
can return 409 rather than the existing request. The preflight fingerprint search
also considers only the latest 100 approvals. Approval decisions call canonical
`decide()` before `execute()`; canonical `decide()` rejects an already EXECUTED
approval, so retrying a completed successful decision cannot reach the execution
callback's replay guard.

This does not establish duplicate execution or approval bypass. It can make a
lost-response retry appear to fail even though the requested change occurred.

**Evidence:** TenantControlService lines 207–230; ApprovalService lines 103–113
and 177–180.

**Action:** Resolve replay by stable request/approval identity before current-state
mutation checks, with consistent actor and full-payload conflict validation.
Acceptance: request retries after state advancement and approval retries after
EXECUTED return the prior outcome without duplicate mutation or audit events;
conflicting key reuse still returns 409.

## Controls supported by the review

- Session, origin and platform permission guards protect platform routes;
  mutation transactions recheck platform permissions.
- New tenants are created inactive; ownership cannot be granted to the operator.
- Profile writes, compliance decisions and membership changes use tenant locks,
  audit-backed replay and version checks when a profile exists.
- Compliance separates editor/reviewer; lifecycle separates maker/approver and
  rechecks activation readiness at execution.
- Dedicated authoring has no intended wallet/ledger/booking or credential grants;
  ordinary API write grants were preserved.
- Cross-tenant RLS and explicit Settings context have passing HTTP coverage.
- Revocation is revalidated on subsequent authenticated access; final-owner and
  self-escalation protections have targeted tests.
- Audit responses omit raw payloads; unsupported finance/upload/invitation/closure
  features are visibly gated.

These are bounded conclusions from inspected code and targeted tests. The audit
immutability response test does not itself attempt SQL UPDATE/DELETE; additional
negative permission tests should accompany A-04.

| Directory | No last-activity filter | Server-supported filter and consistent semantics |
| Finance | No approved financial position reads; editable review metadata is not a finance approval | Integrate canonical approved finance surface; preserve no-write boundaries |

| Suspended servicing | Queue/finance views only | Approved refund/cancellation workflows with preserved gates |
| Closure | No retention/closure workflow | Approved retention policy and non-destructive governed closure |
| Accessibility | Partial keyboard/mobile checks | Complete WCAG review, including focus restoration and assistive technology |

## Recommended order and acceptance

1. Keep PR #300 draft and block production release until A-01 is resolved.
2. Fix A-02 and A-05 with focused legacy/retry tests.
3. Complete A-04 authoring-role certification before production provisioning.
4. Resolve A-03 and execute concurrent directory load tests.
5. Complete the intended enterprise feature scope or obtain an explicit,
   documented reduced release scope; validate its integrations and accessibility.
6. Review the final code, migration/provisioning plan, rollback and exact-SHA CI
   evidence before approving production actions.

No deployment, production provisioning, merge to main, booking/payment enablement
or application remediation was performed as part of this audit.
