# ADR 0032: Explicit runtime write set for the API database role

## Status
Accepted for the API code, tests and two forward migrations (`202610170001`, `202610180001`), replayed only on disposable local databases. Applying them to a persistent database is an owner-controlled step. Resolves open decisions D1 and D2 of ADR 0031 and supersedes its option A/B/C discussion.

## Context
ADR 0031 revoked the Admin authoring writes from `fbeds_api` and left one decision with the owner: which principal writes those tables. The owner has now decided: **least privilege with an explicit, documented write set on the runtime role**. A write is granted only where a reachable, supported workflow proves it is needed; everything else stays revoked. Repository evidence confirms a single principal serves every request (`PrismaService`, one `DATABASE_URL`) and that there is no second API role, so a workflow either runs on `fbeds_api` or is a privileged path performed outside the API process.

## Decision
1. **One definition.** `apps/api/src/database/runtime-role-contract.ts` defines every read and write: table, operation, columns, service, endpoints, reason. Provisioning statements, the live verifier, the 403/503 classification, the generated matrix in `docs/strict-runtime-db-role.md` and the drift specs all derive from it. A spec regenerates the forward migration from it and fails on any difference; another proves every runtime Prisma/SQL write in the source tree is either in the contract or a listed privileged path, and that every granted write has a call site.
2. **Granted writes** (REQUIRED), each exercised end to end through HTTP on the real role (`strict-runtime-role-workflows`), with coverage checked from database statistics:
   `Agency` I,U; `AgencyMember` I,D; `AgencyCreditLimit` I,U,D; `ApprovalRequest` I,U; `CommercialMarkupRule` I,U; `DistributionRestriction` I,U; `ServiceCase` I,U; `ServiceCaseNote` I; `HotelProfile` I,U; `HotelExternalIdentifier` I,D; `HotelAmenity` I,U,D; `HotelImage` I,U,D; and `Hotel` UPDATE on eleven columns only (`name, property_type, country_code, city, address, latitude, longitude, time_zone, star_rating, content_status, updated_at`). The profile, images-adjacent, status, amenities and publication workflows all write the hotel row, so granting `HotelProfile` alone would not make them work; the column list is exactly what they write.
3. **PRIVILEGED PATH** (no privilege, or read only): `SupplierMutation` (journal of gated booking mutations), `RoomAmenity` (rooms workflow writes `RoomType`), `InventoryPool` and `InventoryPoolDay` writes (pool authoring also writes `RatePlan` and `DailyAvailability`), supply core tables, tenant settings, platform administration, identity creation, booking, hold and finance tables. `HotelSearchIndex` maintenance is an operator job.
4. **HotelImage is readable** because its writes are granted: Agent search shows primary images again and the Agent image route works on the strict role (resolves D2).
5. **Error semantics for a database denial on an authorized request** (`DatabaseDenialInterceptor`): compare the live privileges for the denied table with the contract.
   - Equal: the role is intentionally not allowed this operation: **403 `RUNTIME_ROLE_OPERATION_PROHIBITED`**, an audit event `runtime_role.operation_prohibited`, nothing written (the transaction rolled back), no SQL, table or column in the response.
   - Different: the grants drifted: sanitized **503 `DATABASE_ROLE_NOT_PERMITTED`** with a structured diagnostic. This is configuration, not a caller decision.
   - Unattributable to a table: the global filter answers 503 as before. Application RBAC (401/403/404) is unchanged and always runs first. Nothing maps database errors to 403 wholesale.
6. **Credit view.** The committed-holds figure of an agency's credit position reads `InventoryPool`-independent `InventoryHold`, a privileged read. When it is not readable the view reports `committedUnavailable: true` with null amounts (unknown, never zero) so a successfully applied limit change never answers an error. Hold-time enforcement stays fail closed (ADR 0024).
7. **Verifier** compares table-level and column-level INSERT/UPDATE, table-level DELETE/TRUNCATE and every read with the contract, in both directions (an extra privilege and a missing one are both failures).
8. **Migrations.** `202610170001` (ADR 0031) revokes and grants the control reads. `202610180001` converges the sixteen historically granted tables plus `Hotel` on the contract (revoke all, then exactly the contract). Both are no-ops when the role does not exist, so provisioning is authoritative in either order. A spec forbids any later migration from granting to the role.

## Consequences
- The Admin Clients, Commercial markup, Distribution, Service and Hotel Setup/Images/Amenities/Publication modules work on a strict deployment. Supply authoring, Quick Update, pool authoring, rooms, tenant settings and reconciliation answer the typed 403 until a privileged path exists for them (a separate architecture decision; not built here).
- The role can now write the hotel row's eleven columns and the commercial controls, which Agent search and recheck read. Every write is protected by application RBAC (including maker-checker separation of duties for markup, suspension, credit and publication) and forced RLS; the audit trail is insert-only.
- Rollback: the owner re-grants per table (listed in the migration headers) or reverts the contract module and re-provisions. No schema, index, RLS-policy or data change.
