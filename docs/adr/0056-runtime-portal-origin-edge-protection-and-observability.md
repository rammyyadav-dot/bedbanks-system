# ADR 0056: Runtime portal API origin, layered edge origin protection, and observability sinks

Status: accepted for implementation in WP3 (nothing applied to AWS). Extends ADR 0040 and ADR 0055.

## Context
ADR 0055 required immutable image-digest promotion and CloudFront in front of production. Two facts blocked that: the Next.js portals froze the API origin at build time (`next.config` rewrites), and the stack had no edge and none of the logging that the security review listed as open.

## Decisions
1. **Runtime API origin for Agent, Admin and Supplier.** The `/api/v1` proxy moves from `next.config` `rewrites()` to a Node-runtime `proxy.ts` that resolves `API_INTERNAL_URL` on every request through one shared, tested resolver (`tools/deployment/runtime-api-proxy.mjs`). Hosted configuration is validated the same way as before (HTTPS, non-loopback, exact `/api/v1`); an invalid hosted configuration fails closed with a fixed-code `503` and `no-store`, never with the configured URL. A containment guard rejects dot-segment and encoded-dot-segment paths so the proxy can only reach `/api/v1/*` on the API origin (the internal Swagger UI is not reachable through a portal). Explicit `/api/v1` matchers ensure dotted paths (exports) are proxied. The session cookie stays host-only on the portal origin; request cookies and bodies pass through unchanged.
   - Consequence: `Dockerfile.web`, `aws-images.yml` and the Turbo cache keys no longer carry `API_INTERNAL_URL`, `AUTH_API_ORIGIN`, `AUTH_COOKIE_NAME` or `SUPPLIER_ORIGIN`; `PORTAL_HOSTED=1` is now set in the image's run stage. One build is promoted unchanged between environments. Vercel keeps working (its project environment variables are available at runtime).
   - **Exception: the website.** It has no API dependency, but its canonical URLs, sitemap and JSON-LD are built from `NEXT_PUBLIC_*` values at build time. Making them runtime values means dynamic rendering of an SEO-critical site and a new verification of canonicals, so it is not done here. A website image still serves one environment; this is recorded as an open item, not as digest promotion.
   - Cross-account promotion is a registry copy of the digest (for example ECR replication or `imagetools create`), not a rebuild. This is a procedure, not yet implemented.
2. **Edge origin protection in four layers** (`edge.tf`, `network.tf`, `alb.tf`): (a) the public ALB security group admits only the CloudFront origin-facing managed prefix list on 443; (b) ALB listener rules forward only requests carrying `X-Origin-Verify` with one of two rotating secrets (the prefix list is shared by all CloudFront customers, so (a) alone does not exclude another account's distribution); (c) a CLOUDFRONT-scope WAF (managed rules, a 100/5 min limit on `/api/v1/auth/`, a general limit, and for staging an IP allow-list that blocks everything else); (d) the regional WAF stays on the ALB. CloudFront VPC Origins (a private ALB with no public listener) would remove the public ALB entirely and is the recommended hardening once it can be proven in staging; it was not adopted blind.
3. **One distribution per portal host.** Several portals serve identical paths such as `/_next/static/*`; separate distributions guarantee separate cache keys. The API is not behind CloudFront.
4. **Cache policy.** Everything is uncached by default (HTML, server actions, login, search, rate rechecks, mutations, anything personalised or tenant-specific). `/api/v1/*` is explicitly uncached so a future change to the default cannot cache it. Only content-hashed `/_next/static/*` uses the optimized cache policy. Enforced by `check:aws-governance` and its mutation tests.
5. **Client address behind CloudFront.** With CloudFront then the ALB, the client is the second-to-last `X-Forwarded-For` entry. The website gains `TRUSTED_PROXY=aws-cloudfront-alb` (set by Terraform when the edge is enabled); a lone entry is not trusted.
6. **Encryption key policy.** The data KMS key gets an explicit policy so CloudWatch Logs can use it and CloudWatch alarms can publish to the alarm topic, which now uses the CMK. Previously encrypted log groups would fail to create and alarm notifications to an `alias/aws/sns` topic are dropped.
7. **Observability sinks** (retention, redaction, cost levers in `docs/aws-log-retention-policy.md`): VPC flow logs, ALB access logs to a private TLS-only bucket, regional and edge WAF logs with `Authorization`/`Cookie` redacted and only BLOCK/COUNT kept, RDS `postgresql`/`upgrade` export with `log_statement = ddl` (never `all`), Enhanced Monitoring.
8. **Redis AUTH.** An AUTH token over TLS, generated by Terraform and stored as the `REDIS_URL` secret. This puts the token in encrypted state (documented and accepted as proportionate for a cache credential; database credentials remain out of state). Rotation is manual and rolling (`docs/aws-secret-rotation-runbook.md`). RBAC users with command ACLs are a possible later tightening.

## Not decided here / owner decisions
Retention numbers (interim defaults only), the CloudFront access-log destination, whether to adopt VPC Origins, whether to accept the exceptions in `docs/aws-checkov-exception-register.md`, and the website's runtime-URL design.

## Verification
`terraform test` (mock provider), `check:aws-governance` with mutation tests, checkov, tflint, actionlint+ShellCheck, `tools/deployment/certify-runtime-origin.mjs` (one built artifact, two backends). Live-account and image-digest checks are BLOCKED without credentials/Docker; see `docs/aws-wp3-verification-evidence.md`.
